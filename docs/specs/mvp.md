# 年収打 MVP 仕様書

IT エンジニアのチャット返信を模した、ブラウザ上で動くタイピングゲームの MVP 仕様。  
技術選定・実装方式は本仕様の対象外とする。

**UI/UX の視覚方向は、主要画面の HTML モック（A / B / C）を比較し、C. スレッド / DM で確定した。詳細は「12. UI/UX」。**

---

## 1. プロダクト概要

### 1.1 仮称

**年収打（ねんしゅうだ）**

寿司打のように「打って稼ぐ」感覚を残しつつ、スコアをゲーム内年収として見せるための仮称。正式名称は後続で変更してよい。

### 1.2 一言で言うと

相手から届いたチャットに対し、指定された返信文をローマ字で打ち切って送信する。制限時間内に送り終えた返信の獲得額合計が、そのプレイの年収（メインスコア）になる。

### 1.3 プレイ体験の核

1. Slack 風の画面で、今どきの IT 企業のやり取りをしているように見える。
2. 返信を 1 通送り終えるたびに年収が加算される。
3. 入力はローマ字。漢字かな交じりの返信を、ふりがなを頼りに打つ。
4. 結果では年収が主役。速度・正確性などはサブ情報。
5. プレイを重ねると、苦手キー / 指 / キー遷移が分析画面に溜まる。

### 1.4 世界観

- 舞台はトラブルが多めの、今どきの IT 企業。ワークスペース名は **ピンチワークス**。
- 主人公はフルスタックに Web アプリを開発する部署へ配属されている。
- チャンネル例: `#general` `#prod-alert` `#review` `#customer-success` `#random`
- 相手役の例:
  - 佐藤（PM）
  - 田中（先輩エンジニア）
  - 鈴木（デザイナー）
  - 山崎（カスタマー成功）
  - 顧客・山田（社外）
  - 井上（CTO）

### 1.5 主人公の口調ルール

返信文はすべて主人公が打つ文として書く。次を必ず守る。

- カタカナ語が好き。使えば使うほどカッコいいと思っている。
- 1 返信につき、冗談またはボケを 1 つ入れる。入れないと気がすまない。
- 自分は面白いという絶対的な自信がある。
- 難易度が上がるほど、その自信とカタカナ語の密度が上がる。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| プレイ | 難易度と制限時間を選んで開始し、時間切れで終わる 1 回のゲーム |
| 通 | 相手 1 メッセージと、それに対する指定返信 1 件の組 |
| 獲得額 | 1 通を送り終えたときに加算される金額 |
| 年収 | そのプレイで得た獲得額の合計。メインスコア |
| 必要キー | その返信をローマ字で打ち切るために必要なキー入力（正解キー）の列 |
| ミス | いま求めている正解キー以外の印字キーを押したこと |
| 連続入力数 | ミスせずに正解キーを打ち続けた長さ |

## 3. ゲームの流れ

```
ホーム → プレイ → 結果
  │               │
  └──→ 分析 ←─────┘
```

1. ホームで難易度と制限時間を選ぶ。
2. プレイ開始。相手メッセージが表示され、指定返信の入力が始まる。
3. 返信を打ち切ると自動送信され、獲得額が年収に加算される。続けて次の通が届く。
4. 制限時間が 0 になると入力を打ち切る。打ち途中の返信は不成立（0 円）。
5. 結果画面で年収とサブ指標を見せる。
6. このプレイのキー統計を蓄積し、分析画面から確認できる。

ホームと結果の両方から分析へ行ける。分析からホームへ戻れる。

## 4. 画面一覧

MVP の画面は次の 4 つ。

### 4.1 ホーム

目的: 世界観を伝え、難易度と制限時間を選んでプレイを始める。

置くもの:

- タイトルと短いリード（ピンチワークスで返信して年収を稼ぐ、程度）
- 難易度 3 択（初級 / 中級 / 上級）。選んだものが分かる
- 制限時間 3 択（30 秒 / 1 分 / 2 分）。選んだものが分かる
- 開始アクション
- 分析画面への導線
- 直近のベスト年収など、任意の小さな実績表示（無くても開始できる）

### 4.2 プレイ

目的: 今打っているスレッドに没入したまま、タイピングに集中する。見た目の骨格は 12.4（スレッド / DM）。

置くもの:

- 1 本のスレッド本文（左寄せの相手吹き出しと、右寄せの自分の返信）
- スレッド先頭の文脈（相手名、チャンネル名、Issue / PR など）
- いま打つ返信の表示（漢字かな交じり＋ふりがな）
- ローマ字の入力進捗（打済み / いまのキー / 未打）
- 入力欄（コンポーザ）
- HUD: 残り時間、現在年収、選択中の難易度（フローティングピル）
- 直近の通で得た獲得額の短いフィードバック（任意だが推奨）

相手の次メッセージは、直前の返信が成立したあとに出す。同時に複数通を打たせない。

### 4.3 結果

目的: 年収を主役として見せ、サブ指標と次の行動を渡す。

置くもの:

- 年収（いちばん大きく）
- 難易度と制限時間
- 成立した通数
- サブ指標: 入力速度、正確性、ミス数、最大連続入力数
- もう一度（同じ設定で再プレイ）
- ホームへ戻る
- 分析を見る

### 4.4 分析

目的: これまでのプレイから、苦手を確認する。

置くもの:

- 苦手キー（入力回数、ミス回数、ミス率）
- 苦手な指（物理キーと指の対応で集計）
- 苦手な動き（連続する 2 キーの遷移）
- ホームへ戻る

データが少ない初回でも、画面自体は出す。件数が足りない項目は「まだ集計できる通数が足りない」と出す。空のグラフ枠だけは置かない。

## 5. 入力ルール

### 5.1 表示と入力の分担

- プレイヤーが見る本文は、漢字かな交じりの日本語（英数字・記号を含む）。
- 読みが必要な語にはふりがなを付ける。
- プレイヤーが打つのはローマ字（および返信に含まれる英数字・記号そのもの）。
- IME による日本語変換は使わない。変換入力は MVP 対象外。

### 5.2 ローマ字

- 標準的な訓令式／ヘボン寄りの複数表記を許容する（例: `si` / `shi`、`tu` / `tsu`、`zi` / `ji`、`n'` が必要なケース）。
- 許容したどの経路でも、必要キー数はその経路の実際のキー数で数える。
- 英数字・記号は表示どおりのキーで打つ。
- 改行が必要な複数行返信では、改行も必要キーに含める。
- URL のように入力負荷だけが高い長い記号列は出さない。

### 5.3 ミスと進行

- いま求めている正解キー以外の印字キーはミス。カーソル（次に打つ位置）は進まない。
- Backspace で進捗を戻す必要はない。間違えても正解キーを押せば先に進む。
- 修飾キー単独、フォーカス移動、リロードなどはミスに数えない。
- 1 通の全必要キーを打ち切った時点で自動送信する。送信ボタンや Enter 確定は不要。

### 5.4 時間と成立

- タイマーは最初の通の入力が可能になった時点から減る。
- 0 になった瞬間にプレイ終了。その時点で未完成の返信は不成立、獲得額 0 円。
- 時間切れと同時に最後の 1 キーが正解だった場合のみ、その通は成立してよい。

## 6. スコア

### 6.1 メインスコア（年収）

年収 = そのプレイで成立した各通の獲得額の合計。円単位の整数。小数は切り捨て。

```
1通の獲得額 = 基本給(難易度) × 速度係数 × 正確性係数
```

不成立の通は 0 円。成立 0 通なら年収は 0 円。

### 6.2 基本給

| 難易度 | 基本給（1 通） |
| --- | --- |
| 初級（新米エンジニア） | 1,200,000 円 |
| 中級（慣れてきたエンジニア） | 2,200,000 円 |
| 上級（つよつよエンジニア） | 3,500,000 円 |

1 分プレイで数通送れれば、年収らしい桁（数百万〜二千数百万）になることを意図した値。実装前の調整で ±20% 変えてよい。

### 6.3 速度係数

その通の所要時間（入力可能になってから成立するまで）と、必要キー数から出す。

```
実測 kpm = 必要キー数 ÷ 所要秒 × 60
速度比   = 実測 kpm ÷ 基準 kpm
速度係数 = clamp(0.60, 1.50, 0.60 + 速度比 × 0.60)
```

- 基準 kpm は MVP では 180 とする（ローマ字キー/分）。
- `clamp(min, max, x)` は x を min 以上 max 以下に収める。
- 所要時間が 0 以下になることはない。最低 0.1 秒として扱う。

目安: 基準どおりなら係数 1.20、かなり遅いと 0.60 付近、かなり速いと 1.50。

### 6.4 正確性係数

その通について:

```
正確性係数 = max(0.50, 1 - (その通のミス数 ÷ その通の必要キー数))
```

必要キー数よりミスが多い通でも、係数は 0.50 を下回らない。

### 6.5 サブ指標（プレイ全体）

結果画面に出す。年収の内訳計算には使わない。

| 指標 | 定義 |
| --- | --- |
| 入力速度 | 成立した通の必要キー合計 ÷ 入力に使った秒合計 × 60。単位は kpm。小数第 1 位まで |
| 正確性 | `1 - (全ミス数 ÷ (全必要キー数 + 全ミス数))` を百分率。小数第 1 位まで |
| ミス数 | プレイ全体のミス回数 |
| 最大連続入力数 | プレイ全体で、ミスせずに正解キーを打ち続けた最大長 |

入力に使った秒は、各通の所要時間の合計とする。通と通の合間は含めない。成立 0 通のときは速度を「—」、正確性はミスだけでも算出できる場合は出し、必要キーもミスも 0 なら「—」。

### 6.6 獲得額の表示

- 加算時は「+1,560,000 円」のように通ごと見せると分かりやすい。
- 結果の年収は 3 桁区切り（例: 8,240,000 円）。

## 7. 難易度

難易度と制限時間は独立。ホームで別々に選ぶ。

### 7.1 初級（新米エンジニア）

- 短い返信。1 行、おおよそ 20〜45 文字（表示上の日本語）。
- 記号は少なめ。あっても `!` `?` `、` `。` 程度。
- やり取りは確認・簡単な依頼返し・短い進捗。
- 口調は社会人としての初々しさ。カタカナ語とボケは入れるが、 technobabble は抑える。

### 7.2 中級（慣れてきたエンジニア）

- 少し長め。1〜2 行、おおよそ 45〜90 文字。
- `@` メンション、Issue / PR 番号、軽い Markdown（`` `code` ``、`*`、短いリスト）、英数字・記号を含む。
- 口調はちょっと調子に乗り始める。カタカナ語が増える。

### 7.3 上級（つよつよエンジニア）

- 長め、複数行。おおよそ 90〜160 文字。
- Markdown、引用（`>`）、技術用語、英数字・記号を多く含む。
- 口調は自分に絶対的な自信がある。ボケもカタカナ語も遠慮しない。
- それでも URL や長いトークンは出さない。

## 8. コンテンツ方針

### 8.1 題材（必ず含める種類）

MVP のシナリオセットは、次の種類を難易度をまたいでカバーする。

- 確認・レビュー依頼
- バグ報告への返信
- 進捗報告
- 質問への返答
- 顧客への連絡
- `@` メンション
- Markdown 風の構造（コード、リスト、引用）
- Issue / PR 番号
- 英数字や記号を含む文

1 プレイ中は、選んだ難易度のプールから重複しにくい順で出す。足りなくなったらシャッフルして再利用してよい。

### 8.2 出してはいけないもの

- `https://` から始まる URL や、同等に長いパス
- 実在の個人情報、実在顧客の機密を模した具体的すぎる値
- 差別・ハラスメント・過度な自傷や攻撃
- 入力対象としての絵文字連続、IME 依存の文字

### 8.3 1 通の持ちデータ

各シナリオは少なくとも次を持つ。

- id
- 難易度
- 題材タグ（レビュー、バグ、進捗、など）
- チャンネル名
- 相手の表示名と役割
- 相手メッセージ（表示文）
- 指定返信（表示文）
- ふりがな（読みが必要な箇所）
- ローマ字の正答（許容ゆれの代表形）

### 8.4 MVP の本数目安

各難易度 12 本以上。2 分プレイでも極端な繰り返しが起きにくい量。  
本仕様には判断用のサンプルのみ載せ、全本の原稿はコンテンツ作業として後続する。

### 8.5 サンプル

以下は仕様確認用。モックの文言もこれに合わせる。

#### 初級 — 確認

- チャンネル: `#review`
- 相手: 佐藤（PM）
- 相手: `PR #123 のレビューお願いできますか？`
- 返信: `確認します。少々お待ちください。コーヒーのチャージが先ですが。`

#### 初級 — 進捗

- チャンネル: `#general`
- 相手: 田中（先輩）
- 相手: `ログイン画面、今日中に終わりそう？`
- 返信: `アサインされた範囲は本日中にクローズ予定です。ボタンの位置でちょっと格闘してます。`

#### 中級 — バグ

- チャンネル: `#prod-alert`
- 相手: 田中（先輩）
- 相手: `@you 本番の検索、0件になることある。再現手順まだです`
- 返信: `@tanaka キャッチしました。Issue #482 切って調査に入ります。ゼロ件はゼロ距離で向き合います。`

#### 中級 — レビュー

- チャンネル: `#review`

## 9. タイピング分析

### 9.1 取得するもの（プレイごと）

正解・ミスのたびに、次を残す。

- 期待していた物理キー
- 実際に押した物理キー（ミス時）
- 直前に正解した物理キー（2 キー遷移用。通の先頭は無し）
- 難易度、プレイ日時

集計はユーザー単位で蓄積する（同一ブラウザで続きが見られる想定）。アカウント機能は持たない。

### 9.2 苦手キー

キーごとに:

- 入力回数: そのキーを正解として求められた回数（ミスしてやり直した要求も 1 回ずつ足してよいが、MVP では「そのキーが期待されていたイベント数」とする）
- ミス回数: そのキーが期待されているときに別キーを押した回数
- ミス率: ミス回数 ÷ (正解として成立した回数 + ミス回数)

分析画面ではミス率が高い順に上位を出す。入力回数が極端に少ないキーは、参考扱いまたは除外する（目安: 累計 10 回未満は順位から外す）。

### 9.3 苦手な指

JIS 配列の物理キーと指の対応で、苦手キーと同じ指標を指単位に足し上げる。

対応（ホームポジション前提）:

| 指 | 主なキー |
| --- | --- |
| 左小指 | `1` `q` `a` `z` および左側の記号類 |
| 左薬指 | `2` `w` `s` `x` |
| 左中指 | `3` `e` `d` `c` |
| 左人差 | `4` `5` `r` `t` `f` `g` `v` `b` |
| 右人差 | `6` `7` `y` `u` `h` `j` `n` `m` |
| 右中指 | `8` `i` `k` `,` |
| 右薬指 | `9` `o` `l` `.` |
| 右小指 | `0` `-` `p` `;` `/` および右側の記号類 |
| 親指 | スペース |

Shift を伴う記号は、記号キー側の指で数える。Shift 自体は指集計に入れない（MVP を単純にするため）。

### 9.4 苦手な動き

連続する 2 キー（バイグラム）を単位にする。

- 例: `t` → `a`、`s` → `h`
- 指標は苦手キーと同じ（出現回数、ミス回数、ミス率）
- ミスは「2 キー目を期待しているときに外した」場合に、その遷移へ付ける
- 分析画面ではミス率の高い上位を出す。出現が少ない遷移は除外（目安: 累計 8 回未満）

3 キー以上のパターン、速度つきヒートマップ、個人差モデルは対象外。

---

## 10. 画面遷移と状態

- ホームの選択（難易度・時間）は、次のプレイ開始まで保持してよい。
- プレイ中にホームへ戻る操作を置く場合は、そのプレイを破棄する。途中年収は残さない。
- 結果を見る前に閉じたプレイは、年収としては残さなくてよい。ただし途中まで取れたキー統計は残してよい。
- 分析は累計。プレイ 0 回でも画面は存在する。

---

## 11. MVP の対象外

- 技術スタックの決定
- アカウント、ログイン、複数端末同期
- ランキング、シェア画像の必須化
- マルチプレイ、観戦
- IME 変換での日本語入力
- URL や長大トークンのタイピング
- 効果音・BGM を必須にすること（後から足してよい）
- 高度な分析（時系列推移、練習ドリル自動生成、3 キー以上）
- キーボード配列のカスタム（JIS 以外）

---

## 13. 永続化（実装方針）

- タイピング問題とプレイ結果は D1 に保存する。
- 問題は少なくとも相手メッセージ、返信文、返信の読み、難易度を持つ。
- プレイ中のキー入力はブラウザ内で記録・集計する。高頻度イベントを API に送らない。
- ゲーム終了時に結果を 1 回まとめて保存する。
- 初回アクセスで匿名 ID を生成しブラウザに保存する。ログインは無い。個人情報は保存しない。

## 12. UI/UX

### 12.1 共通の方向（確定）

- Slack でやり取りしている風のチャット画面にする。
- 今どきの IT 企業っぽいテイスト。
- 白をベースに、パステルカラーを多数使い、カラフルでポップにする。
- ゲームの HUD（残り時間・年収）は、チャットの雰囲気を壊しすぎない位置に置く。
- 主要情報の優先度: プレイ中は「打つ文」と「残り時間 / 年収」。結果では「年収」。分析では「苦手の上位」。

### 12.3 比較したパターン

判断用 HTML は `mockups/` に残す。文言と必須要素は 3 案とも同じ。

- **A. Slack ワークスペース**  
  左にチャンネルとメンバー、中央がタイムライン、下がコンポーザ。HUD はチャンネルヘッダー。いちばん「仕事の Slack」に近い。
- **B. 年収 HUD 重視**  
  Slack の骨格は残すがサイドは細い。年収とタイマーを常時大きく出す。ゲーム寄りのポップカード。
- **C. スレッド / DM フォーカス**  
  サイドバーなし。1 本のスレッド吹き出しが主役。HUD はフローティング。会話没入寄りのカジュアル。

### 12.4 採用した方向

**C. スレッド / DM** を採用する。参照モックは [mockups/pattern-c.html](../mockups/pattern-c.html)。

確定する骨格:

- サイドバーは置かない。画面中央に 1 本のスレッド（吹き出し）を置く。
- スレッド先頭に相手名と文脈（チャンネル名・Issue / PR など）を短く出す。チャンネル一覧は出さない。
- 相手メッセージは左寄せ、自分の返信は右寄せの吹き出しにする。名前と役割を添える。
- 下部はコンポーザ。その直上に、打つ返信（ふりがな付き）とローマ字進捗を置く。
- HUD（残り時間・現在年収・難易度）はスレッドの上にフローティングのピルで置く。B のような画面幅いっぱいの巨大メーターにはしない。
- 成立した通の吹き出し内に、獲得額（例: `+1,200,000 円`）を短く出す。
- ホーム / 結果 / 分析も同じ中央カラム＋白カード。会話に没入するカジュアル寄せを保つ。
- 色は白ベースにスカイ／ミント／ピーチのパステル。吹き出しは incoming を薄いスカイ、outgoing をミント。

採用しないもの:

- A のような左サイドのチャンネル／メンバー一覧。仕事場の Slack 全体ではなく、今打つスレッドだけを見せる。
- B のような、年収を画面上部いっぱいに出す常時巨大 HUD。
